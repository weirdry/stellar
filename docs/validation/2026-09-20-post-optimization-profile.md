# Optimized CLI CPU and allocation study

Date: 2026-09-20

Scope: [issue #29](https://github.com/weirdry/stellar/issues/29), following the
integration of [PR #28](https://github.com/weirdry/stellar/pull/28) at
`0b557c352c34e8b9594d70f607d67f8bd9b28bad`. This study changes optional contributor
tooling and documentation, not the product or its dependency/runtime contract.

This dated study retains its original measurements and comparison recommendation.
The subsequent [hybrid](2026-09-20-native-normalize-comparison.md) and
[standalone](2026-09-21-standalone-normalize-comparison.md) studies record later
experiments separately. The accepted direction after those studies is to retain
Node, plan TypeScript adoption in [issue #33](https://github.com/weirdry/stellar/issues/33),
exclude Go and defer Rust migration. The proposal below is historical context,
not a request to start another native experiment.

Source inspection explains these sampled owners:

- [Normalization](https://github.com/weirdry/stellar/blob/0b557c352c34e8b9594d70f607d67f8bd9b28bad/lib/normalize.js) still does provider conversion,
  identity/alias construction, relation handling, capture/schema checks and draft
  validation. Its share grows substantially between the small control and the
  50,000-issue input. This is the clearest bounded computation candidate.
- [Continuity](https://github.com/weirdry/stellar/blob/0b557c352c34e8b9594d70f607d67f8bd9b28bad/lib/continuity.js) validates saved state before and after
  transformation; `writeRun` validates again before publishing files. Those
  assertions include map validation and saved/current consistency checks.
  The measured validation cost is not permission to omit any final invariant.
- The relation callback at bundled line 7487 belongs to
  [map validation](https://github.com/weirdry/stellar/blob/0b557c352c34e8b9594d70f607d67f8bd9b28bad/lib/validate.js): endpoint checks, relation identity
  construction, duplicate detection and parent-map construction. Samples on
  that callback do not isolate the old parent-diagnostic scan, which is already
  removed, or prove a new single-expression bottleneck.
- [Reading/rendering](https://github.com/weirdry/stellar/blob/0b557c352c34e8b9594d70f607d67f8bd9b28bad/lib/render.js),
  [CLI dispatch](https://github.com/weirdry/stellar/blob/0b557c352c34e8b9594d70f607d67f8bd9b28bad/lib/cli-commands.js) and `writeRun` account for parsing,
  stringification and writing. Native JSON/encoding work can appear as self
  time in its JavaScript caller. This study does not claim an exact independent
  percentage for each JSON operation, disk wait or individual schema compile.

GC sampled-time medians were 8.51% for 50,000 normalize, 7.25% for 50,000 refresh,
and 6.14% for 10,000 classify. The small normalization control has only 19.77%
under `normalizeCapture`; the remaining samples include loading, schema setup,
encoding, runtime/GC and other work. They are not all removable startup cost.
The previous startup experiment and its missing-schema behavior remain relevant;
no lazy-loading prototype is adopted here.

## Proposed Go/Rust comparison boundary

State: **Open** at the time of this study; subsequent results and the accepted
direction are linked above.

Use the **complete `normalize CAPTURE OUTPUT` command** as the first comparison
candidate. It has a substantial computation share at 50,000 issues, one input
and one output, and no saved user-state transformation or browser dependency.
Keep JavaScript as the reference. This is an experiment recommendation, not an
accepted implementation change or a claim that Go or Rust is faster.

The comparison must retain:

1. The selected command's complete capture/schema and draft-semantic validation,
   provider/namespace identity rules, source facts/raw data, context coverage,
   relation direction/deduplication, ordering and error behavior. Use the same
   algorithm where possible; distinguish algorithm changes from language gains.
   [Normalizer tests](https://github.com/weirdry/stellar/blob/0fe3abb5bf044812bc63a6519fe188e7c5fefbee/test/normalize.test.js),
   [CLI tests](https://github.com/weirdry/stellar/blob/0fe3abb5bf044812bc63a6519fe188e7c5fefbee/test/core.test.js), schemas and implementation own that
   behavior, including failure/no-output and safe output replacement semantics.
2. Complete output equivalence and deliberate invalid/collision cases before
   timing. The large fixture does not cover every identity/error case. A faster
   implementation missing fields, validation or diagnostics is not comparable.
3. Uninstrumented fresh-process wall/CPU/peak-RSS measurements on identical
   captures at 1,000/10,000/50,000 issues, with small-command and startup costs,
   repetitions, ordering, machine/toolchain/build identities and raw samples.
   JSON reading/writing, native build mode and one-time build costs must be
   explicit. Do not compare an optimized native build with a different contract.
4. The integration shape actually proposed: a standalone native command can be
   compared end to end first. A later Node/native helper comparison must include
   Node startup, process/FFI invocation and all serialization/data transfer,
   separately from isolated native function time. Do not assume the helper
   inherits the standalone command's advantage.

Do not begin with a native hash lookup, a validator fed already-parsed data, or
HTML generation alone and extrapolate it to the whole CLI. Refresh/classify
include saved-user decisions and multiple invariant checks; their larger total
cost does not make them the smallest faithful first port. Browser responsiveness
remains unrelated to these command measurements. Deep-chain parent traversal is
also a separate algorithmic shape absent from this balanced-tree benchmark;
this study makes no improved claim for it.

## Verification and limits

- `just ci`: 87/87 Node tests passed with zero skips, plus documentation, eight
  diagram sets, formatting, lint and bundle/manifest currency. The unchanged
  optional benchmark regression suite also passed 4/4 tests separately.
- `just profile-test`: three deterministic tests passed, covering unequal CPU
  sample weights, recursive inclusive attribution, malformed sample/delta
  pairing, heap self/inclusive accounting, frame-path normalization and retained
  self-weight conservation.
- A separate size-100 benchmark and `just profile ... 1` passed all eight
  CPU/allocation output comparisons. All 36 full-run summaries also conserve
  self attribution: listed plus unlisted equals the recorded total.
- Four disposable controls passed: existing output is refused without changing
  its result bytes; changed input and staged-runner bytes fail before profile
  output creation; a Node wrapper appending a byte to the child output is caught
  before any successful profiler `results.json`. The wrapper is a negative
  control only, not a timing or resource measurement.
- This is macOS arm64 evidence. Linux process-RSS units follow the existing
  procedure but were not exercised here. No Windows or alternative Node version
  was tested. Three samples and sampling estimates have workstation variance.
- Final repository and hosted checks are recorded in the delivery PR. No new
  browser/perceptual review, installed-skill invocation, Go/Rust implementation,
  live collection, release, capacity guarantee or runtime acceptance is claimed.
